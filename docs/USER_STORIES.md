# ShipLock — product narrative, real-world user story & milestones

**Tagline:** AI writes the code. Agents pay for independent review. Humans authorize exactly what gets merged.

**Status:** Hackathon product concept, not yet demonstrated as a deployed application. ETHGlobal Mumbai, November 2026.

## 1. Why this matters today

Developer teams are handing autonomous coding agents implementation work and receiving more agent-authored pull requests. GitHub reports 55% of monthly active Copilot users use agentic features and over 90% year-over-year growth in AI-assisted code review usage (2026 Octoverse). This increases throughput but also intensifies *review and authorization* pressure. GitHub already has CodeQL, security scanning, branch policies, and checks; ShipLock is not a substitute. It connects **independently purchased review evidence** to a **freshly authenticated human's approval of the exact revision**, enforcing that match at the merge boundary.

## 2. Problem statement

Small teams cannot manually scrutinize every line generated by agents; specialized third-party audits are often sold as subscriptions or require manual billing; and approvals may become stale when an agent force-pushes new commits. 'The scan passed' is different from 'this person approved this exact code and the repo merged only that revision.'

## 3. Target customer and job to be done

Primary: a maintainer of a small open-source payment SDK, wallet integration, smart contract library, or CI tool with high-consequence changes and limited security-review staffing.

**JTBD:** 'When an AI agent opens a sensitive PR, I want an affordable, on-demand expert/automated audit with verifiable evidence, then I want to authenticate and approve the exact checked commit without letting the agent merge another revision.'

Secondary: teams operating several coding agents; agencies delivering code for clients; open-source maintainers handling untrusted contributors.

## 4. Real scenario — one complete job

A coding agent is assigned to fix an x402 payment validation edge case in a disposable test repository representing a wallet SDK. It opens PR #7 with head `abc123…` (illustrative).

1. **Propose:** ShipLock reads the PR metadata and exact head SHA; labels it `requires paid review` because it modifies payment/signature logic.
2. **Buy:** the coding agent discovers a scanner's published price, receives HTTP 402, checks its per-review spend cap, signs a Hedera testnet HBAR payment, and obtains a paid audit report. No human approved the micro-purchase.
3. **Evaluate:** the scanner returns concrete line-numbered findings, rules version, source SHA, report digest, and an explicit `pass` / `block` / `inconclusive` outcome. The agent cannot set its own review status.
4. **Authorize:** a maintainer enters a World ID Agent Pass step-up flow. A secure backend validates OIDC and session binding; the UI then displays the exact repo, PR, SHA, risks, and merge action. The maintainer separately clicks **Approve this revision**.
5. **Execute:** the backend re-fetches head SHA and GitHub required-check status, verifies single-use authorization, then calls GitHub's merge API with that expected SHA. If the PR has changed, GitHub returns a conflict and no merge happens.
6. **Prove:** the user sees the actual Hedera payment receipt, audit digest, validated-authentication status (without leaking identity tokens), and GitHub merged PR URL.

**Adversarial replay:** After approval, the agent pushes another commit `def456…`. ShipLock rejects the stale approval, leaves the PR open, and requests a fresh paid audit and human authorization. If World authentication is denied or cancelled, the merge is also blocked.

*Note:* The sample PR number and SHA above are illustrations, not real deployed evidence.

## 5. User stories with acceptance criteria

**US-01 — Delegate paid review**
As a coding agent, I want to purchase a PR audit over x402 under a configured budget so I can obtain review evidence without manual API billing.
- The unpaid request receives standard HTTP 402 with immutable price and recipient.
- A valid paid retry yields a real result and Hedera testnet transaction ID.
- A wrong amount, payee, chain, expired quote, or duplicate settlement is rejected or reconciled safely.

**US-02 — Review exact code**
As a maintainer, I want findings tied to a specific PR head SHA so I can see which source revision was actually analyzed.
- Results include repo, PR, SHA, scanner version, findings and digest.
- Blocking or inconclusive findings cannot silently become `pass`.

**US-03 — Authorize one merge**
As an accountable maintainer, I want a fresh World ID authentication followed by explicit consent to merge that exact version so an agent can't infer my permission.
- World OIDC state/nonce/PKCE and ID token validated server-side, with issuer/subject/freshness/assurance checks.
- Approval is bound to repo, PR, SHA, operation, identity, expiry and consumed once.
- Cancellation, mismatch or expiry blocks the action.

**US-04 — Stop stale approval**
As a repo owner, I want the system to block merges if new commits arrive after approval.
- Before merge, re-fetch head SHA, PR mergeable state, required checks and authorization.
- GitHub API merge includes expected `sha`; mismatch triggers 409 and no merge.
- No bypass of protected branch settings; required GitHub status check is a recommended enforcement upgrade.

**US-05 — Inspect proofs**
As a judge or reviewer, I want independently inspectable proof of the agent's paid request, protected approval path and result so the demo is credible.
- Hedera HashScan tx link, real audit content, GitHub PR URL, and denial flow are available.
- Simulated World credentials and local tests are clearly distinguished from real production identity assurance.

## 7. Future uses, without overclaiming

**Near term:** integrate with GitHub Actions and required checks, support multiple independent scanner providers, add signed review manifests and organization-specific sensitivity policies.

**Next:** protect package publication and production deployment using exactly the same operation hash and human checkpoint, with dedicated release evidence.

**Longer term:** a per-request marketplace where coding agents compare audit providers on price, capabilities and reputation, and where team release policies can procure multiple reviews without manual onboarding. These are potential directions, not implemented MVP features.

## 8. What it is not

- Not a claim to detect all malicious code or certify a PR is secure.
- Not a replacement for GitHub native checks, codeowners, repository rules or human review.
- Not cryptographically independent merely because the scanner and buyer live on separate services; provider independence and signatures need additional evidence.
- Not a guarantee of enforcement against GitHub administrators who can bypass protection rules. A required GitHub status check and non-bypass policies strengthen deployment.

## 9. Hackathon pitch — spoken version

'AI coding agents can ship pull requests faster than small teams can review them. Existing CI catches many errors, but it does not automatically answer a different question: which human approved the exact version that was reviewed? ShipLock solves that handoff. An agent discovers an independent review API, pays for it automatically using x402 on Hedera, and gets a report bound to one commit. Before merging, the maintainer completes World ID Agent Pass authentication and explicitly approves that exact revision. If the agent changes the code afterward, approval is invalid and GitHub rejects the stale SHA. We can show a real paid review, a real approved merge, and a blocked changed-code attempt. Today it protects GitHub PRs; next it can protect deployments and package releases.'
